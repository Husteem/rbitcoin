Security
- **One sender can no longer replace the whole address book.** In a full
  book, a source netgroup (IPv4 /16, IPv6 /32, or ASN with `--asmap`) that
  already taught 512 of the 8,192 rows cannot evict another row. Before,
  one IP could replace every untried row in about six minutes. A book with
  room still takes every address from one peer, so a seed or addr-fetch
  reply can fill an empty book. Sources are kept in memory only; rows
  loaded from `peers` after a restart start uncharged.
- **Automatic outbound peers take one netgroup each, grouped as Core's
  `GetGroup`.** Refill, stale-tip replacement, and IBD dials open at most
  one automatic outbound connection per IPv4 `/16`, IPv6 `/32`, or asmap
  ASN, and leave a slot empty rather than reuse a group. Inbound peers no
  longer hold a group. Manual peers are exempt from the rule, though a live
  manual peer still holds its group for automatic dials; Tor, I2P, CJDNS,
  and unroutable peers are exempt. IPv6 addresses that embed an IPv4
  (mapped, NAT64, 6to4) group as that IPv4, Hurricane Electric
  `2001:470::/32` groups by `/36`,
  and an address the asmap does not cover keeps its prefix group. After an
  outage, a paced refill pass redials one clearnet peer and may add one Tor
  or I2P row.
- **A peer's parked headers are walked once per message.** An `inv` or
  `headers` message used to walk the peer's unconnected header chain once
  per item, so one 50,000-item `inv` cost about 17 s of CPU and thirty
  peers could stall the node for half a minute. A message now costs its
  items plus the parked headers.
- **One group of peers can no longer stop the node from requesting other
  peers' transactions.** The process-wide cap of 200,000 announcements is
  gone. Each peer has its own cap of 5,000 (Core
  `MAX_PEER_TX_ANNOUNCEMENTS`), and its rows go when it disconnects.
- **A `getdata` of many announced wtxids reads the tip once.** Block,
  compact block, and `getblocktxn` requests for a stored side block 30 days
  or more behind the best header return before the body is read.
- **A wide Esplora history page stays inside `--max-sh-creates`.** A
  `from_height` window, and a newest-first page of a script with more
  creates than the page limit at any cursor (including a bound inside the
  8,064-block history window), take the same cap and heavy-join turn as an
  unpaged read. A newest-first page of a script with no more creates than
  the limit is still served. Electrum
  `blockchain.scripthash.subscribe` records a hash only after its status is
  computed, so a refused status is not left watched.
- **API transaction tests and broadcasts can no longer fill the script
  pool.** Esplora, Electrum, BlindBit and RPC transaction tests,
  broadcasts and packages ran their script checks on the pool block
  validation uses, with no limit beyond the listeners' request caps. They
  now share one lane of half the script workers, at least one, so on a
  pool of two or more workers block validation keeps the rest.
  Peer-relayed transactions are not affected.
- **A peer that sends invalid headers is disconnected.** A `headers`
  message whose headers connect to our chain but fail the header checks
  (proof of work, difficulty bits, or a time at or below the median) was
  dropped without scoring the peer, so it could resend such batches
  forever and keep its slot. As in Core, that peer is now disconnected
  and discouraged; manual and `noban` peers stay. A time too far in the
  future is still not the peer's fault.
- **Esplora `/block-template` builds are shared and reused.** The cached
  template was dropped on every mempool change, and concurrent requests
  that missed it each built their own, so a few hundred parallel requests
  could keep every core busy. As in Core's `getblocktemplate`, a template
  is reused for a mempool change until it is 5 seconds old, and a request
  that finds a build running waits for it, holding no store-read permit,
  and shares its result.
- **Compact filter requests are served off the network threads.**
  `getcfilters`, `getcfheaders` and `getcfcheckpt` read up to 1,000
  filters (or 2,000 filter headers) from disk on the async worker that runs
  every peer session, so a few peers asking for large ranges could stall
  all P2P traffic. With `--block-filter-index`, those reads now run on the
  blocking pool under the header-work permit, and a peer past its send
  budget is not served.
- **An Electrum idle deadline survives a passive push.** A client that
  subscribed to one scripthash and then sent nothing was never closed: the
  50 ms scripthash tick and every tip or mempool push ended a select pass, and
  the next pass rebuilt the read timeout. One deadline now covers the
  connection; only a complete request line or a silent-payments history step
  clears it, so a slow scan is not cut mid-history.
- **An Esplora response has a minimum drain rate.** The no-progress deadline
  reset on any accepted write, so a reader that took a few bytes before each
  deadline held its socket and accept slot for as long as it chose. A response
  write may now spend at most the request-timeout grace plus
  `bytes-written / --esplora-min-drain-rate` (default 16 KiB/s; NixOS
  `services.rbitcoin.esplora.minDrainRate`) in stalled time. Server compute
  between writes is not counted.
- **The discourage list keeps recording when full.** Misbehaving
  addresses, rate-limit strikes and paused netgroups were kept in maps of
  at most 10,000 entries that ignored new keys once full, so one IPv6
  network could fill the list and nobody who misbehaved in the next day
  was kept out. A new entry at the cap now evicts the oldest, as Core's
  rolling filters do.
- **An oversized Electrum batch is refused before it is parsed.** A batch
  line was turned into a full JSON tree before the 345-item limit was
  checked, so a 1 MiB line of tiny items took about 16 MiB per connection
  before it was refused. The items are now counted without building
  anything, and a batch past the limit gets `batch too large` at once.
- **An Electrum batch holds at most 1 MiB of unwritten replies.** A batch
  ran up to half the blocking pool's reads at once, and the replies that
  finished waited in memory while the first one was written. A client that
  asked for a large transaction several times in one batch and read
  slowly held several copies of it per connection, which across many
  connections could take gigabytes. A finished reply that would take a
  connection past 1 MiB beside the others is now dropped and read again
  when its turn to be written comes.
- **A new block checks Electrum scripthash subscriptions with a set lookup.**
  Each block loaded the full history list of every subscribed script that
  had any history, to see whether the block touched it. One connection
  could hold 10,000 busy public scripts, and many connections could do the
  same, so every block cost millions of list entries. Each block's script
  hashes are now read once, shared by every connection, and a subscription
  is checked against that set without loading its history.
- **A new block restatuses only the Electrum outpoint subscriptions it
  touches.** Every block looked up and pushed every outpoint subscription
  of every connection, up to 10,000 each, so a few clients could turn each
  block into millions of store reads. Each block's created transactions
  and spent outpoints are now read from the store and cached for every
  connection, and only the subscriptions they touch are looked up and
  notified, with those whose mempool spender changed since the last
  notification (a pool lookup, no store read). A reorg, a skipped or
  missed tip, or a block that cannot be read still restatuses every
  subscription, and so does the tip after a status that could not be read.
- **An Electrum outpoint's confirmed-spent status reports the spending
  block's height.** It reported the current tip, so the status changed on
  every block without anything happening to the outpoint.
- **One Electrum connection runs at most 3 silent-payment history scans at
  once.** The process runs 32 scans, and each connection could subscribe
  16 addresses that scanned at the same time, so two connections could
  take every slot for hours and refuse everyone else. A connection's
  fourth and later subscribes are now accepted and scanned in turn with
  the slots its own scans finish with. Filling every slot takes 11
  connections instead of 2.
- **An empty `headers` message no longer runs a header job.** Each one
  cloned the peer's map of up to 8,000 parked headers twice, cloned its
  requested-block set, and waited for a header-pool permit that honest
  header sync shares. A peer could send empty `headers` in a loop to burn
  about a core. An empty reply now just answers the getheaders.
- **Slow Esplora uploads no longer hold request slots.** A `POST` took one
  of the `--esplora-max-inflight` slots before its body arrived, so clients
  that sent their bodies very slowly could hold every slot for the
  two-minute request timeout and lock everyone else out of Esplora. The
  body is now read first, under its own permit and a 30-second deadline,
  and only then does the request take a slot.
- **Esplora outspends look up a transaction once, not once per output.**
  `GET /tx/:txid/outspends`, and each transaction of `/txs/outspends`,
  resolved the transaction id again for every output before reading its
  spend. A transaction with tens of thousands of outputs made each request
  repeat that lookup per output. It is now resolved once and each output
  reads only its own spend.
- **An Esplora response write has a timeout.** A client that stops reading
  can no longer hold the connection and its accept slot. A write that makes
  no progress is cancelled at the request timeout, the same bound the
  internal history body uses. Electrum's writer uses its idle deadline over
  the whole write.
- **Messages sent during the handshake get the same size checks as after
  it.** Before `verack`, frames were decoded without the checks that
  refuse an oversized `headers`, inventory or transaction count before
  allocating, so a peer could make the node allocate for counts its
  payload could never hold. Such a frame now closes the connection, as it
  does after the handshake.
- **A history window reads spends per create, not per block.** An Electrum
  `get_history` with a `from_height`, or an Esplora newest page whose page
  bound fell within 8,064 blocks, read the inputs of every block in that
  window to find spends. A script with one output made every such request
  cost up to 8,064 blocks of reads. Those spends now come from the spend
  slots of the script's own outputs, so the work follows the script's
  create count, which `--max-sh-creates` already bounds.
- **Inbound eviction follows Core's `SelectNodeToEvict`.** When inbound
  slots were full, the peer to drop was predictable. Among equal netgroups
  the one with the lowest network prefix lost, and the netgroup protection
  favoured the lowest prefixes. A peer connecting from chosen networks
  could push out honest peers one by one. Netgroups are now ordered by a
  secret per-process key. A tie goes to the group with the newest member.
  Half of the remaining peers are kept by uptime, with a share reserved
  for onion, local, I2P and CJDNS peers, and up to 8 block-relay-only peers
  that send blocks are kept. The 10-minute refill wait for an evicted
  netgroup is unchanged.
- **More P2P item counts are checked against the frame before decode.**
  An `addr`, `addrv2`, `inv`, `getdata`, `notfound`, `getheaders`,
  `getblocks`, `cfheaders`, `cfcheckpt` or `getblocktxn` whose
  count needs more bytes than the frame has left is now refused before the
  decoder reserves memory for that count, as `tx`, `block`,
  `cmpctblock` and `blocktxn` already were. The peer is disconnected
  like for any oversize message. Core decodes the frame, fails at the end
  of the data, and keeps the peer (#1988).
- **A headers message no longer copies the peer's pending headers.** Each
  non-empty `headers` message cloned the sender's parked headers (up to
  8,000) several times, and each compact block once more. A peer that kept
  that map full and then sent one-header messages made every message cost
  those copies. The map now moves into the header job and back, and the
  batch is staged in place and undone. A message that evicts nothing costs
  its own headers. One that must make room in a full map still scans the
  parked headers once, as before.
- **Repeated handshake messages no longer flood the log.** A redundant
  `version` or `verack`, and every received `addrv2`, each wrote an INFO
  line, so peers could make the node log at their message rate. As in
  Core, these are now `p2p` debug lines, and an oversized `addrv2` is
  refused before it is serialized to count its bytes.
- **Replacement and cluster checks run before script checks.** A
  transaction that conflicts with the mempool but pays too little to
  replace it, or that would overfill its cluster, used to be refused only
  after its signatures and scripts were verified. A peer could resend such
  a transaction and make the node verify it again each time. Both checks
  now run first, as in Core, so the refusal costs no script work. A
  transaction that fails both is now reported with the replacement or
  cluster error, as in Core.
- **The recent-rejects filter no longer fills up.** It stopped recording
  after 4,096 rejected transactions until the next block, so a peer could
  fill it with cheap junk and make the node download and check every later
  rejected transaction again. It now holds up to 120,000 entries, as Core
  does, and drops the oldest when full.
- **A peer can no longer grow `bytesrecv_per_msg` without limit.** Every
  received command name got its own key, kept for the life of the
  connection, so a peer that sent made-up commands grew the node's memory
  by about a gigabyte an hour. A command outside Core's message list now
  counts as `*other*`, as in Core.
- **One replacement may conflict with at most 100 clusters, as in Core.**
  There was no limit, so one transaction could evict any number of cheap
  transactions it conflicted with, along with all their descendants, under
  the mempool write lock. A replacement whose conflicts sit in more than
  100 distinct clusters is now refused with `too many potential
  replacements` (Core `MAX_REPLACEMENT_CANDIDATES`).
- **REST can no longer take every store-read permit.** With `--rest`,
  each REST request held a permit from the store-read budget that
  Electrum, Esplora and RPC share while it built its reply, so a few large
  requests such as `/rest/mempool/contents.json` could stall every other
  store read. REST's reads now count against its own limit of that budget,
  as every API surface's do (see the store-read budget entry), and a
  budget of one still gives REST the only permit in turn.
- **TCP RPC clients can no longer lock out the local RPC socket.** The TCP
  listener and the unix socket shared one 256-connection cap, taken when a
  connection was accepted and before authentication, and a `401` kept its
  connection open. Anyone who could reach `--rpc-listen` could hold every
  slot without a password, so `rbitcoin-cli` (including `stop`) on the unix
  socket was refused. Each listener now has its own cap, and a `401` closes
  its connection.
- **RPC and REST replies have a write deadline.** A client that asked for
  a large reply (for example `/rest/block/<hash>.bin` with `--rest`) and
  then stopped reading kept the reply in memory and its connection slot
  for as long as it liked. As on Esplora, a reply write that makes no
  progress for 30 seconds now closes the connection, and so does a reply
  whose writes spend longer blocked, in total, than 30 seconds plus one
  second per 16 KiB written.
- **Transaction announcements share one global rate limit.** A burst of
  accepted transactions no longer queues one INV per peer. A count bucket
  (14 tx/s, 420 capacity) and a size bucket (20 kB/s, 50 MB capacity) release
  wtxids once for every peer; outbound peers refill both buckets at 2.5x.
  Excess transactions wait in one backlog per direction (inbound and
  outbound) instead of a per-peer queue, so a
  flood cannot multiply INV work by the peer count. A full bucket may
  overdraw to Core's -70 count / -50 kB size floor. Incoming INVs still
  handle each txid and wtxid once per message.
- **Inbound peers no longer win every transaction request.** The node
  asked the first peer to announce a transaction for it at once and waited
  up to a minute before asking anyone else, so an inbound peer that
  announced first and never answered could delay most new transactions by
  about a minute. As in Core, an inbound peer without `noban` is now asked
  only 2 seconds after its announcement, so an outbound peer that
  announces in that time is asked instead.
- **Block size and weight on an unstamped range are rebuilt once.**
  Esplora's block summaries fell back to rebuilding the whole block when a
  block's `txstat` rows were not stamped (ranges left by an older store),
  and nothing stamped them, so every request rebuilt it again. The rebuild
  now stamps the rows of an active-chain block, as `getblockstats` does.
